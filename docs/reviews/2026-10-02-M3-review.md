## Database Routines

### T03 — `database/routines/reservations/sp_create_reservation.sql` CRITICAL
**Rating: PASS WITH NITS**

- **SELECT FOR UPDATE PRESENT** — Line 119: `FOR UPDATE OF rr` locks conflicting `reservation_rooms` rows before the overlap count is evaluated
- Procedure uses `BEGIN ... END` with its own transaction ownership as documented
- SQLSTATE codes correct: `45001` (overlap), `45002` (branch mismatch), `45003` (maintenance)
- `NUMERIC(12,2)` used for `v_rate_per_night`
- Rate snapshot taken at booking time from `room_type.daily_rate`
- Overlap query logic correct: `check_in_date < p_check_out AND check_out_date > p_check_in` (half-open interval)
- `'Cancelled'` and `'CheckedOut'` excluded from overlap check

**Nits:**

- **N-01 (Line 158-169, Step 3):** Rate is re-fetched in the second loop even though it was already fetched in Step 1. This causes N extra queries for an N-room reservation. Performance nit only — not a correctness bug.
- **N-02 (Line 107-110):** Comment should note that `FOR UPDATE` has nothing to lock on first booking for a room (no existing rows) — serialization for that case comes from the unique constraint on INSERT. Future maintainers should not remove the lock thinking it is redundant for the overlap case.

const diff = new Date(checkOut).getTime() - new Date(checkIn).getTime();
return Math.max(0, Math.round(diff / (1000 * 60 * 60 * 24)));

2. **Strict:** Remove `countNights` and display the night count only from the API response (after booking confirmation), removing the helper entirely.

The same function appears in `app/guest/reservations/page.tsx` line 73 — same finding applies.
